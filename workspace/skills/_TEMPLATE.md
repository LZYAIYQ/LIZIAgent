# <skill-id>

> 本模板遵循钱学森《论系统工程》的"目标—输入—执行—输出—反馈"控制论闭环，
> 每个 skill 必须给出这五要素的明确定义；缺失任何一项就意味着这个 skill
> 还不能投入运行。模板正文章节用中英双语头方便 LLM 在 prompt 里识别。

## 一、目标 / Goal

> **要素含义**：这个 skill 在系统里要把"什么状态"驱动到"什么状态"。
> 必须**可观测、可验证**——避免"提供有用建议"这类不可证伪的目标。

- 期望产出：<具体的、可量化的最终输出形态>
- 不属于本 skill 的范围：<与之相邻但应由别的 skill 处理的边界>

## 二、触发 / Trigger（输入信号）

> **要素含义**：哪些可观测的输入信号应当激活这个 skill。
> 包含**正向触发**和**反向排除**两类，避免触发面与相邻 skill 重叠。

正向触发：
- <用户原话模式 1>
- <用户原话模式 2>
- <可复用的查询模式>

不要在以下情形使用本 skill：
- <场景 A>——应交给 `<sibling-skill>`
- <场景 B>——属于一次性请求，应走 memory，不要建 skill

## 三、步骤 / Steps（执行控制）

> **要素含义**：受控过程本身。每一步都应当是**独立可校验**的最小动作；
> 步与步之间的状态转移要清楚。LLM 复盘时要能逐步对照自己的轨迹。

1. <步骤 1：动作 + 关键参数 + 校验点>
2. <步骤 2：…>
3. <步骤 3：…>

> 涉及代码 / 调试 / 重构 / 实现方案时，遵循 Karpathy-inspired 原则：
> 编码前思考、简洁优先、精准修改、目标驱动执行。

## 四、输出 / Output（被控变量）

> **要素含义**：交付给"系统外"（用户 / 下游 skill / cron 推送）的最终格式。
> 必须给出**可逐字对照**的样板，不能只描述"语气友好"。

样板：
```

```

约束：
- 长度上限：<例如 ≤500 字符>
- 风格：<简洁、无前置寒暄、无 Markdown 标题…>
- 字段顺序：<必要时强制顺序>

## 五、反馈 / Feedback（偏差检测 + 校正）

> **要素含义**：闭环的最后一环。何时判定"这次执行偏离了目标"？偏离时怎么修正？
> 这一节决定了 skill 的鲁棒性，比"步骤"还关键。
